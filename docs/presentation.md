## スライド3: 提案 — 避難施設 × 災害伝承のAR統合

- **キーメッセージ**: 伝承・史料を「補助情報」として避難施設情報に重ね、避難の理由を体感的に学べるようにした。
- **載せる内容（新規性3点セット）**:
  1. 各避難先カードに**「なぜここへ逃げるか」の理由文**を必ず添付（過去の津波記録に基づく短文）
  2. **記録高ゲージ**: 史料に津波高・浸水深の記録がある地点に、AR空間で「高さの柱」を立てる
     （御穂神社 約1.0m〔浸水深〕・吹合 約6m・江湖 約4〜5m・向島 約3m）

- **トーク**: 「数字で『6m』と言われるより、目の前に6mの柱が立つ方が伝わる。ただし伝承を防災の根拠にはしない——ここが設計の肝」

## スライド6: 技術構成 — 無料で動き、壊れない

- **キーメッセージ**: 全機能が無料・APIキー不要で成立し、外部サービスが落ちても6系統のフォールバックで壊れない。
- **載せる内容**:
  - スタック図: **LocAR.js + three.js + Vite**（WebAR）／Leaflet+OSM（地図）／Overpass API（町並み3D）／
    OSRM（経路）／GitHub Actions＋Pages（CI/CD）。Google Maps・Routes は**キー設定時のみの任意強化**
  - **フォールバック6系統**（図にする）:
    1. 地図: Google Maps → Leaflet+OSM
    2. 経路: Google Routes → OSRM → 直線参考（灰色破線で明示）
    3. ストリートビュー: パノラマ未提供 → 合成3D学習ビューへ復帰導線
    4. 方位センサー: 無し/拒否 → マウス見回し
    5. iOS権限: `DeviceOrientationEvent.requestPermission()` はユーザータップ内でのみ・拒否時はsimへ
    6. 全画面直後の `clientWidth=0` → `window.innerWidth` で仮描画→次フレーム再調整
  - **無料枠を守る設計**: Overpass結果を localStorage 7日キャッシュ／ジオコーディング1req/秒＋永続キャッシュ／
    Google Routesは**表示する1本だけ**呼び、FieldMaskで必要3フィールドのみ要求。候補ソートはOSRM維持
  - 性能: 町並み3Dの**建物数上限1400**で市街地フリーズを防止
- **トーク**: 「研究試作は予算ゼロ・デモ環境不定。『キーが無くても・電波が悪くても・センサーが無くても動く』を最初から設計した」
- **素材・根拠**: README「技術構成」、PR #16（FieldMask・route-only）、PR #21（キー無し時はGoogleスクリプト自体を読まない）、
  `src/ar.js:1090,1147`、コミット ca88780（建物上限1400）。

## スライド7: データの信頼性設計 — 出典のない情報は1件もない

- **キーメッセージ**: 「伝承を防災に使う」からこそ、出典・座標精度・断定表現を仕組みで管理した。
- **載せる内容**:
  - **全61レコード（施設37＋伝承24）に `source_title` / `source_url` 必須**。出典台帳17件（静岡市公式・気象庁・
    国土地理院・法務省登記所地図・査読論文・地域アーカイブ）
  - **confidence（出典の信頼度）と座標精度を別軸で管理**。不確かな座標は「📍おおよその位置」表示、
    確定できなければ**非表示（null）**——「誤った位置を断定するより出さない」
  - **location_kind 4分類**: 点として断定してよいか（exact_point 18／representative_point 4／area_or_line 1／unresolved 1）
  - **CIで自動検査**: `npm run validate:data` がid重複・出典欠落・座標・location_kind整合を全PRでチェック
  - **エピソード（人間の現地照合で仕上げ）**: ジオコーディング不能だった避難タワーの座標を、
    現地・公式サイト照合チェックシートで**9件修正（うち6件は null→実座標）**。同時に、御穂神社のデモ地点が
    境内の中にあったため**OSRMが私有地を通る経路を生成していた**ことが発覚 → 神社出口・公道接点へ座標修正
- **トーク**: 「『座標が正しい』と『経路が正しい』は別問題だった。機械的な検証と人間の現地確認の両方が要る、というのが一番の学び」
- **素材・根拠**: `data_quality.md` §1-3・§5、README「データ構成」、PR #25（現地照合）、`tools/validate-data.mjs`。

- **キーメッセージ**: AIにコードを書かせ、品質と安全性は「ルール×ワークフロー×CI」の3層で仕組みとして担保した。
- **載せる内容**:

  - **第2層 プロジェクトスキル**: 「調査→**範囲宣言→承認待ち**→最小実装→検証→報告」の5フェーズをAIに強制。
    変更禁止範囲（注意文・attribution・live AR・データ構造）を明文化
  - **第3層 GitHub**: main直push禁止（ruleset）／CODEOWNERSでowner承認必須／**CIが通らないPRはマージ不可**／
    AIによる自動マージ禁止。PRテンプレに**11項目のチェックリスト**（「最短」と書かない・出典必須 等）
  - **実績**: PR 26件（マージ15件）。実装前に**案A/B/Cを提示→合意してから着手**（ストリートビュー道順のPR #22）。
    各PRが「目的・設計判断・動作確認・**未検証項目**」を記録——検証できないこと
    （実機のみのAR動作・APIキー必要機能）を**未検証と明示して人間に引き継ぐ**運用
  - **分業**: AI=実装・自動検証（ヘッドレススモーク・単体テスト・既知ベクタ照合）／
    人間=現地照合（スライド7のエピソード）・プレビュー実機確認・マージ判断
- **トーク**: 「AIの出力を信じる代わりに、疑える仕組みを作った。『出典のないデータはCIが落とす』ので、AIも人も混入させられない」
- **素材・根拠**: `CLAUDE.md`、`.claude/skills/miho-safe-project-workflow/SKILL.md`（PR #26）、

## スライド9: 実装で苦労した点（3エピソード）

- **キーメッセージ**: 「正しく案内する」「誤認させない」の細部に一番時間を使った。
- **載せる内容**:
  1. **徒歩経路が車道で計算されていた**: OSRMのプロファイルが車(driving)固定になっており、
     徒歩切替を実装したら**三保の実例で車1.8km→徒歩1.0km**。避難所要時間の推定が大きく変わった。
     以降、徒歩で経路が取れない時も**勝手に車道へ切り替えず**、灰色破線の「直線参考」を明示する方針に
  2. **AR看板の日本語が切れる**: 文字数ベースの折り返しでは日本語・全角・絵文字で破綻 →
     canvas `measureText` による**ピクセル幅折り返し＋`Array.from`で書記素単位処理**に刷新。
     検証も数値で実施（最大行幅510px ≤ 518px でクリップなし／6mゲージのラベル左端4.84m > ボード右端3.64m で非重複）
  3. **Street Viewには「端末の方位」が無い**: 実方位センサーに頼れないため、
     `panorama.getPov().heading`（=見ている向き）を基準に「右へ◯°／✓この向き・約N m」を計算する方式に。
     道なりタップ前進も**1タップ24m上限**にして経路のショートカットを防止（スマホはタップ許容9m・PCは6m）
- **トーク**: 各エピソードを「症状→原因→解決→検証」の型で30秒ずつ。
- **素材・根拠**: コミット ca88780・9318936、PR #20・#22。

### A-1. 経路・ナビの正確さ
